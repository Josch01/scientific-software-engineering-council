## Dirección de producto y prioridades P2–P4 (2026-11-03)

SSEC tendrá dos modos que comparten contratos y evidencia: **Modo A, skill portable** dentro de Codex o Gemini, aprovechando subagentes nativos cuando estén disponibles; y **Modo B, aplicación Centro de Control Científico**, conectada a interfaces locales oficiales del proveedor —CLI o App Server cuando corresponda— sin requerir una API de pago adicional. La aplicación visual será opcional: la skill debe funcionar sin ella. Disponibilidad de CLI, App Server y delegación se detecta por capacidad y se informa como `BLOCKED` o `NOT_RUN` cuando no pueda verificarse; configurar un proveedor no equivale a invocarlo.

| Fase priorizada | Entregable | Criterio de aceptación y límite |
|---|---|---|
| **P2 — Motor científico para el primer caso SIR** | Contrato de modelo y datos, simulación ejecutable y reproducible, oráculos numéricos, errores visibles y resultados trazables. Componentes científicos opt-in para simulación, ajuste y análisis. | Probar ecuaciones/parámetros/condiciones iniciales frente a referencias y tolerancias declaradas; conservar procedencia de datos, configuración y código. No inferir identificabilidad ni validez científica a partir de ajuste, gráfica o tests de software. No ampliar componentes antes de comprobar que los necesita el caso SIR integral. |
| **P3 — Espacios científicos dinámicos** | Núcleo visual estable y opcional más componentes reutilizables configurados por contratos estructurados versionados. Especialistas pueden describir o ajustar el espacio de un proyecto; el código específico queda como artefacto de proyecto revisable. | En el SIR modificado con datos experimentales, configurar ecuaciones/parámetros, simulación/gráficas, optimización e identificación, sensibilidad/error/incertidumbre, resultados/tests/auditorías y código/archivos. El núcleo GUI no se reescribe por modelo. Completar solicitud → especialistas → implementación → pruebas → revisión independiente → resultados → aprobación humana. |
| **P4 — Calidad y entrega 1.0** | Validación adversarial de contratos y artefactos, empaquetado opcional de la app, compatibilidad de modos/proveedores, documentación, benchmarks y catálogo opt-in con procedencia. | Bloquear solo las funciones afectadas por riesgos de uso inseguro; registrar límites experimentales restantes. Release requiere gates de evidencia, revisión de seguridad independiente y decisión humana de licencia/aprobación. No merge a `main`, tag ni publicación automáticos. |

**Primer caso integral de validación:** el usuario entrega un SIR modificado y datos experimentales; SSEC prepara un espacio, implementa una simulación reproducible, ejecuta pruebas, muestra resultados y permite solicitar una auditoría a especialistas. La salida debe distinguir `SOFTWARE_VALIDITY`, `NUMERICAL_VALIDITY` y `SCIENTIFIC_VALIDITY`. La auditoría puede concluir que falta información o que un reclamo no está demostrado; la aprobación sigue siendo humana. Este caso valida el sistema y no certifica automáticamente identificabilidad ni validez matemática del modelo.
